# Wireframes

## Purpose

Describe the initial screen structure before visual design or implementation.

## Goals

- Keep the MVP mobile-first.
- Identify required screens and primary actions.
- Avoid over-designing before playtesting.
- Give implementation a shared layout vocabulary.

## Initial Screen List

### Resume / Start

Primary actions:

- Resume active game.
- Create new game.
- Open documentation or settings only if needed.

### Create Game

Primary fields:

- Game name.
- Ruleset preset.
- Optional event intensity.

### Player Setup

Primary actions:

- Add player.
- Choose color.
- Edit or remove player before start.
- Start game.

### Game Dashboard

Primary zones:

- Current game header.
- Dice entry.
- Player kingdom summary.
- Quick actions: trade, attack, history.

### Kingdom Detail

Primary zones:

- Player identity.
- Resource controls.
- Active bonuses.
- Active penalties.
- Defense status.
- Recent player history.

### Event Resolution

Primary zones:

- Event title.
- Trigger explanation.
- Affected players.
- Effects to apply.
- Confirm or cancel if optional.

### Trade Flow

Primary steps:

- Select players.
- Select offered resources.
- Select requested resources.
- Confirm settlement.

### Attack/Defense Flow

Primary steps:

- Select attacker.
- Select target.
- Show cost and possible result.
- Select defense if available.
- Resolve.

### History

Primary zones:

- Chronological event list.
- Player filter.
- Correction action.

## Open Questions

- Should the dashboard use tabs or a vertically scrollable table view?
- Should dice entry be globally fixed at the bottom?
- Should history be reachable from every screen?
